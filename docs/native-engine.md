# AppShield 原生引擎

桌面管理器、受管启动、权限记录、中转和实验驱动均在本仓库中构建。运行时使用 Windows 已提供的 AppContainer、Job、ACL 和按包 SID 限定的防火墙规则。用户可以从 GPL-3.0-only 源码得到完整实现，无须向第三方申请功能授权。早期的 Sandboxie 研究保存在[对照记录](integration.md)中。

## 一个应用如何运行

1. **登记。** 读取所选 EXE 并记录哈希、版本和路径。通用 EXE 使用本机 Windows 信任库核验嵌入签名或系统目录签名，显示验证结果和发布者。Telegram 还核对指定发布者，商店安装额外核对包族和清单入口。每个配置有独立的 Windows 包 SID 和持久工作区。
2. **保存和应用。** 保存只更新本地配置。应用时为这个 SID 设置只读或可读写的目录 ACL，记录对应的目录标识，核对防火墙 ActiveStore 中的有效规则。权限更新未完成时阻止启动。正在运行的受管程序须先退出，才可替换或撤销权限。
3. **启动。** 根据选定的网络范围创建 capability 列表，挂起创建进程，同时绑定 Job 和包身份。核对实际映像、SID、capability 和剪贴板 Job 标志后恢复执行。一个独立的本地监督进程在 UI 关闭后继续持有该 Job 的句柄。微信使用程序所在目录作为当前工作目录，与官方快捷方式一致，其用户目录、AppData 和临时目录指向配置的私有空间；其他应用采用配置内的工作目录。[Windows 进程启动接口](https://learn.microsoft.com/en-us/windows/win32/secauthz/implementing-an-appcontainer)
4. **中转。** 传入目录对受管程序只读，接收目录可写。宿主只导出用户选中的普通文件，在发布前检查实际文件对象和目录，保留下载来源标记。文本交付及文件导出通过宿主侧按钮触发。

Windows ACL 按文件系统对象授权。向所有应用包开放的资源可能仍然可读，继承被关闭的子项也可能拒绝访问。移动已授权目录可能改变后续路径核对结果，应用或撤销前应确认目录身份。程序安装目录下的附属 DLL 和资源有时需要显式只读授权。直接双击原始程序仍按原来的 Windows 方式启动。

## 实机观察

在 Windows 11 Pro 26H2（build 26300.9974）上通过实际桌面程序接口验证。所有文件和连接对照使用合成数据，公网对照仅与指定端点完成 TCP 握手。

| 项目 | 观察结果 |
| --- | --- |
| 可见进程与状态 | 合成 Win32 客户端恢复执行前通过 SID、能力和 Job 核对，窗口可见。引导程序退出后，不同文件名的子进程仍能被识别，继续接受相同的文件与网络对照。运行时替换权限被拒，退出后可撤销。 |
| 文件 | 宿主能读私有标记。受管进程读私有文件被拒，只读目录的文件可读不可改，可写目录能创建文件，宿主复核了原件和新内容。 |
| 网络 | 离线与仅公网两次试验中，宿主都能连通 IPv4 回环、当前网卡和 IPv6 回环的合成监听器，受管客户端均被阻断。仅公网试验中，受管客户端同时能连到宿主已确认可达的同一个微软公网地址的 TCP 443 端口。各次临时规则和身份已回收。 |
| 剪贴板 | 专用测试窗口站中，普通对照能读写合成文本。加上产品使用的 Job 限制后，测试进程无法取得原文本或发布新文本，但仍可以清空剪贴板。测试未读取交互桌面的剪贴板。[完整对照](../tools/restricted/) |
| 单次文本 | 宿主显式把合成 Unicode 文本交给选定的受管标准 Edit，子进程返回内容匹配确认。持有过期启动时间的目标被拒绝，控件未收到文本。 |
| Telegram | 已由独立引擎导入并应用商店版 7.3.3.0 的配置。仅复制核验过的 EXE，使用独立工作目录并保留其他实验选项。真实程序取得受管身份后提前以状态 0 退出，本轮日志匹配到本地 IPC 监听失败。原账号未迁移，启动前后的 12 个宿主协议值一致。 |

当前持久网络设置支持离线、仅公网、公网加局域网，均使用系统回环隔离。发现该 SID 被授予回环例外或系统无法确认所需防火墙规则时，启动会中止。[Windows 包防火墙规则](https://learn.microsoft.com/en-us/powershell/module/netsecurity/new-netfirewallrule) · [Job UI 限制](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_basic_ui_restrictions)

## 微信未登录验收

2026-11-18 在 Windows 11 x64 上测试了已安装的微信 4.2.0.53。导入会核对 `Weixin.exe` 的本机 Authenticode 信任结果、签名发布者和产品信息。新配置的宿主目录授权列表为空，网络默认仅允许公网。手工选择同一映像、重新发现安装均保留原配置和已保存的权限。启动前如发现另一安装路径的同名进程或旧版 `WeChat.exe`，会将其列为待确认并停止启动。

| 测试 | 实机观察 |
| --- | --- |
| 正常启动对照 | 同一安装的官方程序显示 **Scan to log in**，随后关闭本次实例，未扫码。 |
| 宿主专用标准账户 | 普通权限的 AppShield 在当前 Windows 桌面启动同一官方安装。进程路径、腾讯签名、Windows 账户 SID 和会话均通过核验，同一可见窗口持续三秒显示扫码提示。 |
| 运行时文件保护 | 对合成文件，Windows Authz 使用真实微信主进程令牌评估读取权限，在应用规则前、应用后、撤销后分别为允许、拒绝、允许。同账户探针保持运行并在每阶段实际重新打开文件，结果一致。主账户始终可读，文件内容及目录 ACL 最终恢复。全程未登录，未观察微信主动读取所测文件。 |
| 原启动环境 | 权限、映像和 Job 核对后恢复执行。用原环境分别在私有工作目录和官方快捷方式的程序目录启动，均以 `0xFFFFFFFF` 退出。系统文件事件显示，微信尝试在安装目录下创建数据子目录时被拒绝。 |
| 私有 AppData 适配 | 为配置创建标准的 Roaming、Local 和 Documents 目录，微信能在私有 Roaming 下创建诊断数据，成功加载 Weixin.dll。正式构建仍在稳定显示受管登录窗口前退出，退出码 `0x80000003`。Windows 应用错误记录也报告同一异常，触发它的内部条件尚未确定。 |
| 独立安装副本对照 | 在私有测试目录逐文件比对安装文件的 SHA-256，仅给测试身份两个诊断日志的写权限。副本显示 **Launch Error**，正文提示运行环境异常并要求从官方渠道下载。该结果属于复制后的位置；原安装路径的异常没有显示相同说明。 |
| 文件边界 | 独立随机 AppContainer 中的合成进程对未授权目录读、建文件均被拒绝；只读目录可读，修改和新建均被拒绝；可写目录可创建并读回标记。宿主复核了文件内容。这个实验验证了 Windows 文件权限机制，微信自身的附件操作仍须在客户端能够保持运行后验证。 |

复测时，退出其他微信实例，在普通交互式 Windows 会话运行 `.\tools\Build-AppShield.ps1 -WeChatPreloginTest`。验收要求同一受管窗口持续三秒显示已知的中英文扫码提示；启动错误弹窗和无法确认内容的窗口均不能通过。通过后它终止本轮 Job，并对第二次启动重复验证。验收只匹配固定的界面文字；不会操作登录控件，也不采集二维码。结束后撤销临时授权并删除测试身份。

上面的构建开关测试通用 AppContainer 路径。宿主账户模式的复测入口是 [Test-WeChatHostAccount.ps1](../tools/wechat/Test-WeChatHostAccount.ps1)。在该模式下，Windows 账户配置可随同一个长期账户持续使用。AppShield 单独验证专用账户并为所选 NTFS 目录设置拒读规则；该账户下其他进程也受这些规则约束。已经获取的句柄或数据不受追溯控制，桌面剪贴板和网络沿用宿主设置。

使用 REA 6.9.0 静态核对了 AppShield 自身的编译产物，并修正了启动器非零退出、有受管子进程继续运行时遗漏退出码的问题。合成客户端以 33 退出后，其受管子进程继续运行，实测返回了正确的退出码。修正后的原安装微信在新身份下仍返回 `0x80000003`。

再次排查时，在同一独立 Windows 来宾中先验证原版微信正常启动，再使用相同安装文件和验收程序对比两份 AppContainer 构建。原 Job UI 掩码 `0x46` 与去掉桌面限制的 `0x06` 均在启动阶段返回 `0x80000003`。因此生产原生引擎保留原有保护。客户端内部抛出异常的具体原因仍未确证。

产品微信入口统一使用启动环境选择窗，提供同桌面专用标准账户和一次性 Windows 沙盒。后者仅把已核验安装包所在的专用目录只读映射到来宾，在来宾内安装并核实官方主程序，再请求启动。来宾初始网络默认关闭，显式选择联网时使用沙盒默认网络。AppContainer 页的目录和防火墙授权仅适用于原生诊断路径。普通用户也可从命令行明确指定模式：

```powershell
# $installer 是已下载的腾讯官方 x64 安装包的绝对路径。
.\build\AppShield\AppShield.exe --prepare-wechat-sandbox "$installer"
.\build\AppShield\AppShield.exe --launch-wechat --sandbox-network
.\build\AppShield\AppShield.exe --launch-wechat --sandbox-offline
.\build\AppShield\AppShield.exe --launch-wechat --appcontainer
```

无模式参数的 `--launch-wechat` 与微信受管快捷方式打开同一选择窗。程序只连接本次创建的来宾，沙盒已有会话时会保留它。启动请求返回后，用户可继续观察来宾内的安装或扫码结果。

已分别从正式桌面按钮和 `--launch-wechat --sandbox-network` 启动新来宾。两轮均收到来宾安装回执，同一签名微信进程的扫码提示持续可见至少三秒。来宾能校验唯一的安装包，向宿主共享输入目录新建文件被拒绝。测试最后只关闭各自新建的会话，未扫码登录。CLI 重定向输出在来宾继续运行时也正常返回。

2026-11-18 重启后，在 Windows 11 build 26300、Windows 沙盒客户端 0.8.114.0 中实测了[独立沙盒启动方式](../tools/wechat/README.md)。联网来宾从官方安装包安装微信 4.2.0.53。来宾核对腾讯签名、实际进程映像和窗口归属，同一窗口持续三秒显示扫码提示，宿主通过微软沙盒 CLI 核实本轮回执为 `PASS_SCAN_PROMPT`。全程未扫码或登录。

同一来宾能读取并校验安装包，尝试在唯一的宿主共享目录创建专属空文件时被 Windows 拒绝，宿主确认标记文件不存在。配置关闭了宿主剪贴板、麦克风、摄像头和打印机重定向。联网配置使用默认虚拟交换机，可能访问局域网；沙盒关闭时会清除来宾数据。本轮未验证账号登录、聊天或附件收发。

## 已登录宿主微信的联网控制

Windows 11 上使用 Windows Defender 防火墙，把阻止规则同时限定到一个本地账户的 SID 和一个可执行文件的完整路径。合成客户端在普通用户身份下新建外部 TCP 连接，规则生效时 Windows 返回 WSAEACCES，撤销后重新连接成功。以同一账户运行另一个程序，以及用另一账户运行同一个程序，两组都能在规则生效期间建立连接。测试只完成 TCP 握手。

在已登录的官方微信 4.2.0.53 上，短时应用这条规则，核对 Windows 的有效策略，随后撤销；持久策略和有效策略中均未残留本轮规则。应用前、生效时和撤销后，均采样到当前 Windows 账户有五个已核验的主程序进程、一条已建立的 TCP 连接。连接数是瞬时观察，没有据此推断任何聊天收发或目的地址。

## 微信剪贴板受限启动

在新建微信进程尚未执行时，启动器把它加入指定了 `JOB_OBJECT_UILIMIT_READCLIPBOARD` 和 `JOB_OBJECT_UILIMIT_WRITECLIPBOARD` 的 Windows Job，核实生效标志和进程归属后再恢复执行。该模式可在当前账户或专用账户启动时选择。Job 的限制延续到进程及其正常后代退出；关闭管理器不会关闭微信。

在独立非交互窗口站中使用合成文本对照，普通进程可读写，受限进程无法取得文本或发布新文本，仍可清空窗口站原有内容。另在全新 Windows 沙盒中使用相同启动代码运行官方微信 4.2.0.53，核实主窗口持续三秒显示扫码提示，并观察到受同一 Job 管理的真实后代。此次未在已登录的宿主微信上施加剪贴板限制，未读取宿主剪贴板。

## 驱动与待验收边界

自研 Filter Manager 驱动可由固定版本的 WDK 编译。实验控制器可向内核绑定挂起的合成进程，驱动按进程对象记录不可变策略并让子进程继承。本阶段实现本地 NTFS 已有文件的打开和读写边界，创建、重命名、已存在映射等范围见[驱动说明](../driver/AppShieldFilter/)。本机尚未加载此驱动。编译产物、InfVerif 以及共享路径规则测试均不能代替独立 Windows 内核中的动态验收。

Telegram 当前需要解决的是 Win32 本地监听器的兼容性。另一组独立受限令牌实验中，首次创建默认权限的命名管道成功，随后创建同名监听器被拒，未作为真实应用的备用启动路径。微信的实际登录与文件收发同样尚待验证。
